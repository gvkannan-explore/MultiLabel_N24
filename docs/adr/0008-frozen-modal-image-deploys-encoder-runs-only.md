# Deployments are frozen Modal images of encoder runs only

Only a trained BERT-family encoder is deployed, never a zero-shot LLM, even when the LLM scores higher. The eval harness writes `results/nlp/<run>.json` and zero-shot scoring writes `results/llm/<run>.json`, and `.github/workflows/deploy.yml` starts only on a push to `main` that changes a file under `results/nlp/`. Zero-shot scores are for comparison; their model is a public checkpoint we did not train, and the deployment gate's reproducibility checks have no weights or dataset hashes to judge for it. As a second guard, the image build reads the served checkpoint's own `config.json` and refuses any `model_type` outside the BERT family, so a misplaced results file cannot deploy another architecture.

The deployment is a Modal image that holds its own copy of the checkpoint and code. A `run_function` build step copies the run's `metrics.json` and `best_model/` out of the `n24-runs` volume after checking that the weights' sha256 equals the one the deployment gate judged, so a deployed version keeps serving those weights even if the volume is later overwritten by a retrain under the same name. We considered a Docker image pushed to a registry, which would also be portable outside Modal. On Linux, `uv.lock` pulls the CUDA build of torch, so that image would be several GB, and the CI runner would have to download the weights from Modal, build it, and push it with registry credentials, even though the API runs on CPU. The frozen Modal image gives the same guarantee without moving the weights out of Modal. If the API ever has to run elsewhere, a Docker image becomes worth its cost. The endpoint requires Modal proxy auth, so only callers with the token can spend its compute.
